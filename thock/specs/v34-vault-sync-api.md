## 1. Purpose and how to use this document

Three sessions build V34 at the same time:

| Session | Owns | Reads this document for |
| --- | --- | --- |
| **Backend** (`thock/services/plus`, Go) | the routes of §6, the tables, the feed, APNs, quota and lapse | §3–§6, §11, §12 |
| **Desk** (`crates/thock`, Rust) | the shared core of §9 (rules, hashing, envelope, fixtures), the sync service, the UI | everything |
| **Phone** (Thock iOS, Swift) | the store, the queue, the rebase, pairing, the screens | §3–§5, §7–§10, §11 |

The document fixes everything two sessions must agree on without talking: URLs, bodies, status codes,
byte formats, hashes, the write vocabulary and the rules that apply a write. It deliberately says
nothing about how each side stores its own state (the desk's `.thock/sync/state.json`, the phone's
SQLite, the backend's indexes) beyond what the wire needs.

**What is frozen.** Every route, field, status code, byte layout, hash and application rule in §3–§10.
Tests in each codebase pin them (§12). **What is open.** Anything marked *internal*; the ordering of
work in §11; the wording of error sentences, which the backend may improve as long as the `code` stays.

**Rules of change.** Additive changes (a new optional field, a new event kind, a new error code, a new
route) land with a line in §13 and need no version bump; clients ignore what they do not know. A
breaking change (removing or renaming a field, changing a hash or an application rule) bumps the path
prefix to `/v2/` and the envelope magic, and the fixtures of §9.3 get a new directory. No breaking
change ships before all three sides have a test against the new shape.

Two decisions this contract takes that V34 left open, so the API could be frozen:

- **§16 #1, merge model:** semantic writes from the phone, snapshots from the desk, exactly as V34 §4.2
  and §8 describe. Three-way merge is not part of v1.
- **§16 #2, shared rules:** one Rust crate (§9.1), compiled into the desk and shipped to the phone
  through UniFFI, with a language-neutral fixture corpus (§9.3) so a Swift port stays possible.

And one deviation from V34 §9, explained in §5.2: the associated data of a file blob binds it to its
**path and a client-chosen blob id**, not to its version, because the version is only known once the
blob is committed (§6.3).

## 2. Vocabulary

| Term | Meaning |
| --- | --- |
| **vault** | One Plus user's synced folder. One per user. Identified by an opaque `vault_id`. |
| **device** | The desk or the phone. `role` is `desk` or `phone`; at most one of each per vault. |
| **snapshot** | The full content of one file at one version, uploaded by the desk as an encrypted blob. |
| **write** | One operation from §7, made on the phone, queued on the server, applied by the desk. |
| **version** | A number drawn from one counter per vault, assigned to every published file change (create, update, tombstone). Strictly increasing in publish order, so a single number is also the phone's pull cursor. |
| **seq** | A number drawn from a second per-vault counter, assigned to every accepted write. |
| **cursor** | The highest `version` a client has fully processed. |
| **vault key** | 32 random bytes, generated by the desk, carried to the phone in the pairing QR. The server never sees it. |
| **key check** | `hex(sha256("thock-vault-key-check/1" ‖ key))[0..32]`. The server stores it so a mis-scanned or rotated key is caught on the first call instead of on the first failed decrypt. |

## 3. Conventions

### 3.1 Transport

- Base URL: the Plus backend (`https://plus.thock.app` in production; `http://localhost:8080` under
  `go run .`). Every route below is relative to it and sits under `/v1/`.
- JSON bodies, `Content-Type: application/json; charset=utf-8`, on every request and response except
  the SSE feed (§6.5) and the signed blob URLs (§6.3), whose bodies are raw bytes.
- Request bodies are limited to 64 KB except where a route says otherwise.
- Clients send `Thock-Client: <desk|phone>/<app version>` on every request. Diagnostic only.
- Times are RFC 3339 in UTC with a `Z` suffix: `2026-10-02T14:03:11Z`.
- `version`, `seq`, sizes and counts are JSON integers below 2^53.
- Binary values in JSON (`payload`, `content_hash`) are lower-case hex for hashes and standard base64
  with padding for payloads.
- Unknown fields are ignored by every party; absent optional fields mean their documented default.

### 3.2 Authentication and roles

Every route except `POST /v1/vault/pair` and `/health` needs `Authorization: Bearer <credential>`.

| Caller | Credential | Resolves to |
| --- | --- | --- |
| Desk | its existing Thock Plus credential (`tpk_…`, V25) | the user, and the vault's `desk` device if one exists |
| Phone | the credential minted at pairing (`tpp_…`) | the vault's `phone` device, hence the vault and user |

Each route lists the roles that may call it. A call from the wrong role is `403 role_forbidden`. The
user's Plus entitlement is checked on every call; see §3.4 for what a lapsed entitlement allows.

### 3.3 Errors

Every non-2xx response is

```json
{"error": "One sentence the person can read as is.", "code": "stale_version"}
```

`error` follows the V25 house style (a sentence, no jargon). `code` is new and is what clients branch
on. The full list:

| Status | `code` | When |
| --- | --- | --- |
| 400 | `bad_request` | body unreadable, required field missing, malformed path or hash |
| 401 | `unauthorized` | no credential, unknown credential, or a phone credential that was revoked |
| 403 | `revoked` | the user's Plus access was turned off (V25) |
| 403 | `role_forbidden` | the route is for the other device |
| 403 | `plus_lapsed` | the entitlement ended; see §3.4 |
| 403 | `plan_excludes_sync` | the user's plan has `vault_quota_bytes = 0` |
| 404 | `vault_missing` | the user has no vault yet (desk must `POST /v1/vault` first) |
| 404 | `not_found` | the file, device or write does not exist |
| 404 | `pairing_invalid` | the pairing code is unknown or already used |
| 409 | `stale_version` | `expected_version` is not the file's current version; body carries `current` (§6.3) |
| 409 | `key_mismatch` | `key_check` differs from the vault's and the vault is not empty |
| 409 | `device_exists` | reserved; unreachable while a vault is keyed by its user, so not emitted today |
| 410 | `pairing_expired` | the code's ten minutes are over |
| 410 | `cursor_expired` | `since` is older than the tombstones the server still keeps (§6.3) |
| 413 | `too_large` | a blob or write payload above 2 MB |
| 422 | `path_not_allowed` | path fails §4.1 |
| 422 | `blob_missing` | commit for a blob that was never uploaded or whose size differs |
| 429 | `slow_down` | rate limit; honour `Retry-After` |
| 507 | `quota_exceeded` | the upload would take the vault past its hard cap |
| 503 | `unavailable` | database or blob store unreachable; retry |

### 3.4 Lapse

When `vaults.lapsed_at` is set (V34 §12; also set when the Plus user is revoked or disconnects):

- the phone may still `GET /v1/vault`, `GET /v1/vault/files`, download blobs and hold the feed; every
  `POST`/`PATCH`/`DELETE` from the phone is `403 plus_lapsed`;
- the desk may `GET /v1/vault` and `DELETE /v1/vault`; every other desk call is `403 plus_lapsed`;
- thirty days later the vault's rows and blobs are gone and every call but `POST /v1/vault` is
  `404 vault_missing`.

The feed emits `vault {"status":"lapsed"}` once when the lapse is recorded.

### 3.5 Limits

| What | Limit |
| --- | --- |
| Plaintext file | 2 MB (2 097 152 bytes). Larger files are not synced; the desk lists them. |
| Blob (envelope) | plaintext + 32 bytes |
| Write payload (envelope, decoded) | 2 MB |
| Path | 1 024 bytes of UTF-8 |
| `GET files` page | `limit` default 500, max 2 000 |
| `GET writes` page | `limit` default 200, max 1 000 |
| Signed URL lifetime | 15 minutes |
| Pairing code lifetime | 10 minutes, single use |
| Tombstone retention | 30 days, after which `since` cursors older than the oldest kept tombstone are `410 cursor_expired` |
| Vault quota | `plans.limits.vault_quota_bytes`, 200 MB by default; hard cap is quota + 10 % |

## 4. Paths, versions and identifiers

### 4.1 Paths

A path is the file's location relative to the vault root, as the desk sees it on disk:

- `/` separated, no leading or trailing `/`, no empty segment, no `.` or `..` segment;
- UTF-8, NFC-normalised, at most 1 024 bytes;
- extension (case-insensitive) in `md`, `txt`, `toml`, `json`, `csv`;
- not under `.thock/history/`, `.thock/cache/`, `.thock/sync/` or `.git/`.

The server validates all of this on every route that names a path and answers `422 path_not_allowed`
otherwise. In URLs the path is the tail of the route, percent-encoded per segment (`daily/2026-10-02.md`
→ `/v1/vault/files/daily/2026-10-02.md`; a space is `%20`). Both clients keep paths byte-exact: the
phone never renames, and a desk rename is a tombstone at the old path plus a create at the new one.

### 4.2 Versions and seqs

- `version` comes from one counter per vault and is assigned when a file change is **committed**
  (§6.3) or a tombstone is written, inside a transaction that locks the vault row, so publish order
  equals numeric order. Gaps are legal; clients never assume contiguity.
- `latest_version` on the vault is the highest assigned version.
- `seq` comes from a second per-vault counter, assigned when a write is accepted.
- `acked_through_seq` and `acked_at_version` are recorded on the vault at every ack (§6.4) and are how
  the phone knows when a pending write may be dropped (§8.4).

### 4.3 Identifiers

| Id | Format | Chosen by |
| --- | --- | --- |
| `vault_id`, `device_id` | 16 lower-case hex chars | server |
| `blob_id` | 32 lower-case hex chars (16 random bytes) | the uploading desk, one per upload attempt |
| `client_id` of a write | UUID v4, lower-case | the phone, once per write, stable across retries |
| pairing `code` | 8 chars from `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`, shown as `XXXX-XXXX`; compared without the dash and case-insensitively | server |

## 5. Encryption envelope

### 5.1 Primitive

ChaCha20-Poly1305 (IETF, RFC 8439: 32-byte key, 12-byte nonce, 16-byte tag) with the vault key. One
fresh random nonce per envelope. CryptoKit on the phone, the `chacha20poly1305` RustCrypto crate in the
core; the fixtures of §9.3 include known-answer vectors so the two agree.

### 5.2 Envelope bytes

```
offset  size  field
0       4     magic  "TVS1"  (0x54 0x56 0x53 0x31)
4       12    nonce
16      n+16  ciphertext ‖ tag
```

Associated data is a context string, a NUL, and the binding identifier, all UTF-8:

| Envelope | Associated data | Plaintext |
| --- | --- | --- |
| file snapshot | `thock-file/1` ‖ `\0` ‖ path ‖ `\0` ‖ `blob_id` | the file's bytes, exactly as on disk |
| write | `thock-write/1` ‖ `\0` ‖ `client_id` | the UTF-8 JSON of the write document (§7) |

Binding to `blob_id` rather than to `version` (V34 §9) is because the version does not exist until the
commit step of §6.3 and the blob is encrypted before it is uploaded. A blob still cannot be replayed at
another path, and a given `(path, version)` row names exactly one `blob_id`, so a client can check that
the blob it downloaded is the one the index promised. A server that returns an older row as current is
outside the threat model, as in V34.

`content_hash` is `hex(sha256(envelope bytes))`: the whole envelope, magic included. The server stores
it as declared by the uploader; the downloader recomputes it and treats a mismatch as a corrupt
version to be re-fetched on the next pull, never as a file to apply.

### 5.3 Key material

- The vault key is 32 random bytes from the OS. It lives in the desk's OS keychain and the iOS
  Keychain, never in the vault, never in a request body.
- The pairing QR encodes one URL: `thock://pair?v=1&code=XXXX-XXXX&key=<base64url, no padding, 43 chars>&backend=<percent-encoded base URL>`.
- `key_check` (§2) is the only key-derived value the server ever receives.

## 6. Routes

Summary; details follow. **D** = desk, **P** = phone, **–** = no credential.

| Method and path | Who | Purpose |
| --- | --- | --- |
| `POST /v1/vault` | D | create the vault and the desk device, or confirm they exist |
| `GET /v1/vault` | D P | the vault's status, quota, devices, counters |
| `DELETE /v1/vault` | D | *Turn sync off*: delete every row and blob |
| `POST /v1/vault/reset` | D | rotate the key: wipe files and writes, revoke the phone, record the new key check |
| `POST /v1/vault/pairings` | D | mint a pairing code |
| `POST /v1/vault/pair` | – | redeem a code; mint the phone credential |
| `GET /v1/vault/devices` | D P | list devices |
| `PATCH /v1/vault/devices/me` | P | update name or push token |
| `POST /v1/vault/devices/{device_id}/revoke` | D | *Disconnect phone* |
| `GET /v1/vault/files` | D P | the index, with download URLs |
| `POST /v1/vault/files/{path}` | D | begin an upload: get a signed URL |
| `POST /v1/vault/files/{path}/commit` | D | publish the uploaded blob as the new version |
| `DELETE /v1/vault/files/{path}` | D | tombstone |
| `POST /v1/vault/writes` | P | queue a write |
| `GET /v1/vault/writes` | D | read the queue |
| `POST /v1/vault/writes/ack` | D | prune the queue through a seq |
| `GET /v1/vault/feed` | D P | server-sent events |
| `GET /v1/entitlement` | D P | V25's route, extended with a `vault` object |

### 6.1 Vault

**`POST /v1/vault`** (desk). Idempotent.

```json
{"device_name": "Diego's MacBook", "key_check": "9f1c…32 hex"}
```

→ `200` with the §6.1 vault object. Creates the vault and the desk device on first call. On a later call
the `key_check` must match unless the vault holds no files (`file_count == 0`), in which case the new
check is adopted; otherwise `409 key_mismatch`. A desk device bound to a different user credential is
`409 device_exists` (one desk per vault; the user re-enables sync from the new machine with
`POST /v1/vault/reset`).

**`GET /v1/vault`** (both) → `200`:

```json
{
  "vault_id": "3a9c0d1e5f2b4a67",
  "status": "active",
  "key_check": "9f1c…",
  "created_at": "2026-10-02T14:00:00Z",
  "lapsed_at": null,
  "quota_bytes": 209715200,
  "used_bytes": 48211233,
  "file_count": 1412,
  "latest_version": 1842,
  "writes": {"pending": 3, "latest_seq": 57, "acked_through_seq": 54, "acked_at_version": 1839},
  "devices": [
    {"device_id": "7b2e…", "role": "desk",  "name": "Diego's MacBook", "paired_at": "…", "last_seen_at": "…"},
    {"device_id": "c41a…", "role": "phone", "name": "Diego's iPhone",  "paired_at": "…", "last_seen_at": "…"}
  ]
}
```

`status` is `active` or `lapsed`. `used_bytes` sums the sizes of live blobs. The desk's status row and
the phone's *waiting for the desk* count read from here.

**`DELETE /v1/vault`** (desk) → `204`. Deletes files, blobs, writes, devices and the vault row. The
phone's next call is `401 unauthorized`. The feed emits `vault {"status":"deleted"}` before closing.

**`POST /v1/vault/reset`** (desk).

```json
{"key_check": "e07d…"}
```

→ `200` with the vault object. Deletes every file row, blob and write; revokes the phone device; stores
the new key check; leaves `latest_version` and `latest_seq` where they were (counters never go back).
The desk then re-uploads everything and mints a new pairing. The phone, if still alive, gets
`401 unauthorized` and shows *connect again at the desk*.

### 6.2 Pairing and devices

**`POST /v1/vault/pairings`** (desk) → `201`:

```json
{"code": "K7MP-4QZX", "expires_at": "2026-10-02T14:13:11Z"}
```

Minting a new code invalidates any unused earlier one.

**`POST /v1/vault/pair`** (no credential).

```json
{"code": "K7MP-4QZX", "device_name": "Diego's iPhone", "platform": "ios", "apns_token": "a1b2…hex or null"}
```

→ `201`:

```json
{
  "credential": "tpp_…",
  "device": {"device_id": "c41a…", "role": "phone", "name": "Diego's iPhone"},
  "vault": { …the §6.1 vault object… }
}
```

The phone compares `vault.key_check` with the check of the key it scanned before storing anything; a
mismatch is a scan error, shown as *that code didn't work, try again*. A second phone pairing replaces
the first: the earlier phone credential is revoked and its row removed. Codes are single use:
`404 pairing_invalid` after redemption, `410 pairing_expired` after ten minutes.

**`GET /v1/vault/devices`** (both) → `200 {"devices": [ … ]}` as in the vault object.

**`PATCH /v1/vault/devices/me`** (phone). Any subset of `{"device_name": "…", "apns_token": "…"|null}`
→ `200` with the device object. The phone calls this whenever iOS hands it a new token.

**`POST /v1/vault/devices/{device_id}/revoke`** (desk) → `204`. The phone device's credential stops
working at once. Revoking the desk device is `400 bad_request`; use `DELETE /v1/vault`.

### 6.3 Files

**`GET /v1/vault/files?since=<version>&limit=<n>`** (both) → `200`:

```json
{
  "files": [
    {
      "path": "daily/2026-10-02.md",
      "version": 1842,
      "deleted": false,
      "blob_id": "5d…32 hex",
      "size_bytes": 2242,
      "content_hash": "ab…64 hex",
      "updated_by": "desk",
      "updated_at": "2026-10-02T14:03:11Z",
      "download_url": "https://…",
      "download_expires_at": "2026-10-02T14:18:11Z"
    },
    {"path": "inbox/2026-10-01-0912-call-ana.md", "version": 1840, "deleted": true, "updated_by": "desk", "updated_at": "…"}
  ],
  "next_since": 1842,
  "has_more": false
}
```

- Rows are ordered by `version` ascending, one row per path (the latest). With `since`, every row with
  `version > since`, tombstones included. Without `since`, every live file and no tombstones; this is
  the full pull, after which the client deletes any local file not listed.
- `download_url` is present on live rows and is an opaque URL for a `GET` that returns the envelope
  bytes. Clients skip the download when `content_hash` equals the hash they already hold for that
  `version`.
- `size_bytes` is the envelope size (what the quota counts).
- `410 cursor_expired` when `since` is below the oldest retained tombstone; the client performs a full
  pull.
- On the last page `next_since` is the vault's `latest_version`, so a cursor never lags behind the head
  because of pruned tombstones or a full pull.

**`POST /v1/vault/files/{path}`** (desk). Begin an upload.

```json
{"expected_version": 1801, "blob_id": "5d…", "size_bytes": 2242, "content_hash": "ab…"}
```

`expected_version` is the version the desk last saw for this path, `0` for a path the desk has never
seen (create). → `200`:

```json
{"upload": {"url": "https://…", "method": "PUT", "headers": {"Content-Type": "application/octet-stream"}, "expires_at": "…"}}
```

The desk `PUT`s the envelope bytes to `url` with exactly those headers and `Content-Length: size_bytes`.
Refusals: `409 stale_version` with `"current": {"version": 1839, "blob_id": "…", "content_hash": "…", "deleted": false}` in the body,
`413 too_large`, `422 path_not_allowed`, `507 quota_exceeded`. Because the desk is the only party that
publishes snapshots, a `409` means the desk's own record is behind (state lost, or a second desk); the
desk adopts `current.version` as `expected_version` and retries with the content on disk, which wins.

**`POST /v1/vault/files/{path}/commit`** (desk).

```json
{"expected_version": 1801, "blob_id": "5d…"}
```

→ `200 {"version": 1842, "updated_at": "…"}`. The server checks the object exists with the declared
size (`422 blob_missing` otherwise), re-checks `expected_version` (`409 stale_version`), assigns the
version under the vault lock, updates the row and `used_bytes`, schedules the previous blob for
deletion, emits `file` on the feed and queues a push (§6.5). Committing the same `blob_id` twice is
`200` with the same version. A *begin* for a blob that was already committed is `409 stale_version`
(only the commit is idempotent), so a client retrying after a lost commit answer retries the commit, not
the whole upload. Begun uploads never committed are swept after an hour.

**`DELETE /v1/vault/files/{path}`** (desk).

```json
{"expected_version": 1801}
```

→ `200 {"version": 1843}`. Writes a tombstone, frees the blob, emits `file` with `deleted: true`.
Deleting a path that is already a tombstone is `200` with the existing tombstone version.

### 6.4 Writes

**`POST /v1/vault/writes`** (phone). Body limit 3 MB.

```json
{"client_id": "0f7e0b1a-…", "path": "daily/2026-10-02.md", "base_version": 1839, "payload": "<base64 envelope>"}
```

`base_version` is the version of `path` in the phone's store when the write was made, `0` when the
phone had no such file. → `201 {"seq": 58, "created_at": "…"}`. The same `client_id` again returns
`200` with the original `seq`, whatever the body says: retries are free. Emits `write` on the feed.

**`GET /v1/vault/writes?after=<seq>&limit=<n>`** (desk) → `200`:

```json
{
  "writes": [
    {"seq": 55, "client_id": "…", "path": "daily/2026-10-02.md", "base_version": 1839, "payload": "<base64>", "created_at": "…"}
  ],
  "has_more": false
}
```

Ascending by `seq`, unacked rows only. `after` defaults to `acked_through_seq`.

**`POST /v1/vault/writes/ack`** (desk).

```json
{"through_seq": 58}
```

→ `200 {"through_seq": 58, "at_version": 1845}`. Retires every write with `seq ≤ through_seq` (the row
keeps its `client_id` and `seq` for seven days with the payload emptied, so a late retry of the same
`client_id` still gets its original `seq` instead of a duplicate), records
`acked_through_seq` and `acked_at_version = latest_version` at that instant, emits `ack`. Acking a seq
already acked is `200` with the recorded values. The desk acks only after it has committed the
snapshots that carry the writes' effects (§10.4), which is what makes `at_version` meaningful.

### 6.5 Feed and push

**`GET /v1/vault/feed`** (both). `Accept: text/event-stream`. The server keeps the connection open,
sends `: ping` every 25 seconds, and emits events caused by **the other device only**:

```
event: file
data: {"path":"daily/2026-10-02.md","version":1842,"deleted":false}

event: write
data: {"seq":58,"path":"daily/2026-10-02.md"}

event: ack
data: {"through_seq":58,"at_version":1845}

event: vault
data: {"status":"lapsed"}

event: device
data: {"device_id":"c41a…","revoked":true}
```

Events are nudges, not the record: on connect and on every reconnect a client polls
`GET /v1/vault/files?since=<cursor>` (both), `GET /v1/vault/writes` (desk) or `GET /v1/vault` (phone,
for `acked_through_seq`) regardless of what it did or did not receive. The server may close the
stream at any time (Cloud Run does after an hour); clients reconnect with backoff starting at one
second, capped at a minute. `Last-Event-ID` is not used.

**APNs** (server internal, shape frozen for the phone). When a `file` or `ack` event has no phone
feed to go to, the server sends one silent push per thirty-second burst:

```json
{"aps": {"content-available": 1}, "thock": {"vault_id": "3a9c…", "latest_version": 1842, "acked_through_seq": 58}}
```

The phone treats it exactly like a reconnect: pull, then read `GET /v1/vault`.

### 6.6 Entitlement

`GET /v1/entitlement` (V25) gains one optional object, present when the user has a vault:

```json
"vault": {"quota_bytes": 209715200, "used_bytes": 48211233, "status": "active", "lapsed_at": null}
```

`plans.limits.vault_quota_bytes` joins the plan JSON (`0` means no vault for this plan).

## 7. The write document

The plaintext inside a write envelope. One JSON object, UTF-8, keys as below. The server never sees it.

### 7.1 Common fields

```json
{
  "v": 1,
  "client_id": "0f7e0b1a-…",
  "kind": "replace_line",
  "path": "daily/2026-10-02.md",
  "made_at": "2026-10-02T13:58:02Z",
  "device_id": "c41a…",
  …kind-specific fields…
}
```

`client_id` and `path` repeat the clear-text envelope fields so the desk can detect a payload served
under the wrong row (logged and skipped, never applied).

### 7.2 Headings

Where a write names a heading it is an object:

```json
"heading": {"text": "Day planner", "level": 2, "ordinal": 0}
```

- Matching uses V26's `heading_key(text)` (links reduced to labels, non-alphanumerics folded to a
  space, Unicode-lowercased, whitespace collapsed, trimmed) against every ATX heading in the file,
  **ignoring level**; `ordinal` picks among equal keys in file order (default `0`; out of range → the
  last match). Exact lowercase equality wins over key equality, as in V26 §5.2.
- `level` is used only when the heading must be created (§8.2 rule 2). Default `2`.
- `null` means *the end of the file*.

A heading is a line matching `^#{1,6}[ \t]+\S` outside a fenced code block (` ``` ` or `~~~`, any indent
up to three spaces) and outside a leading frontmatter block (a first line of `---` through the next
line that is `---` or `...`). Setext headings are not headings. Lines in a fence or frontmatter are
never matched by any rule here.

The **section** of a heading is the line range after the heading line up to, not including, the next
heading whose level is less than or equal to the matched heading's level, or the end of the file. Its
**body** is that range with trailing blank lines removed, and without a trailing thematic break
(`___`, `---` or `***` on its own line) and the blank lines before it, since the shipped templates
close every section with `___` and an append must land above it. Its **own lines** are the body up
to, not including, the first deeper heading inside it, with its own trailing blank lines (and a
closing rule) trimmed the same way. A front-matter block that is never closed is ordinary content.
The whole-file body of a `null` heading trims only blank lines: the end of the file is below a
closing rule. A heading's `text` has its closing `#`s and surrounding whitespace removed; a heading
line starts at column 0.

### 7.3 Kinds

| `kind` | Fields | Meaning |
| --- | --- | --- |
| `create` | `content` (string) | create the file with `content` if it does not exist |
| `append` | `heading` (object or null), `lines` (array of strings, no line terminators), `placement` (`"end"` default or `"before_children"`), `blank_line_before` (bool, default false), `create_from_template` (bool, default false) | insert `lines` at the end of the section (`end`: after the body's last line; `before_children`: after the last of the own lines) |
| `replace_line` | `heading`, `line_hash`, `ordinal` (int, default 0), `new_line` | replace one line |
| `remove_line` | `heading`, `line_hash`, `ordinal` | remove one line |
| `replace_section` | `heading`, `base_hash`, `lines` | replace the section's body with `lines` |

Strings never contain `\r` or `\n`; the applier joins with the file's line ending (§8.1).

### 7.4 Hashes

**`line_hash(line)`**, in order:

1. Drop the line terminator. Strip leading whitespace.
2. Strip one list marker: `- `, `* `, `+ `, or `\d{1,9}[.)] `.
3. Strip one checkbox: `[ ] `, `[x] `, `[X] `.
4. Strip one time prefix (V4 grammar): `H:MM` or `HH:MM`, optionally a separator (`-`, `–`, `—` or `to`,
   each with optional surrounding spaces) and a second time, only when followed by whitespace or the
   end of the line; then that whitespace.
5. Repeatedly strip a trailing HTML comment (`<!--…-->`) and trailing whitespace. This is what lets a
   line keep its identity after it gains ` <!--thock:also-->` or a calendar marker.
6. Collapse every run of whitespace to one space; trim.
7. `line_hash = hex(sha256(utf8(result)))[0..16]`.

A line whose result is empty is not addressable; a phone never emits a write against one.

**`section_hash`**: the section body (§7.2) with line endings normalised to `\n`, joined by `\n`, no
trailing newline; `hex(sha256(bytes))[0..16]`. An empty body hashes the empty string.

Known-answer vectors for both live in the fixtures (§9.3).

## 8. Application rules

`apply(existing: Option<text>, write, seed: Option<text>) → (text, outcome)`. Deterministic, total:
every input yields a file, never an error, except a malformed write document, which is rejected before
application. `seed` is the already-expanded template the host supplies when `create_from_template` is
set (the desk through `notes::ensure_note`'s template path; the phone from the synced template file,
expanded with the same tokens). Outcomes: `created`, `section_added`, `applied`, `kept_both`, `noop`.

### 8.1 Text handling

- Line ending: the file's dominant terminator (`\r\n` if it appears more often than `\n` alone),
  `\n` for a new file. Inserted lines use it. A file that ends without a terminator keeps that property
  for its last line when a `replace_line` edits it in place; an insertion after it adds one before the
  new lines, and lines written by `append` or `replace_section` always end with a terminator, even when
  they replace what used to be an unterminated last line.
- Encoding: UTF-8 in and out. The desk never uploads a file that is not valid UTF-8.
- Nothing outside the touched lines changes, byte for byte. This is tested by the round-trip fixtures.

### 8.2 Rules, in order

1. **Effect already present** (§8.3) → `noop`. Checked first for every kind. This gives idempotence
   (a desk crash between apply and ack re-applies safely) and defines what the phone drops on rebase.
2. **File missing.** `create`: the file is `content` → `created`. `append` with `create_from_template`
   and a `seed`: the file is the seed, then continue → outcome at least `created`. Any other write: the
   file becomes the heading line (`#` × level + space + text, `level` default 2) followed by a blank
   line, then continue. `replace_line` / `remove_line` / `replace_section` with no file fall through to
   the target-missing rules below.
3. **`create` on an existing file** with different content: becomes `append` of `content`'s lines at
   the end of the file with `blank_line_before: true` → `applied`.
4. **Heading missing** (and not `null`): the heading line is inserted, preceded by one blank line,
   **before the first level-1 heading that is not the file's first heading**, or at the end of the file
   if there is none. This keeps `# Daily Closure` and friends last. Then continue → `section_added`.
5. **`append`**: insert `lines` after the body's last line (`end`) or after the last own line
   (`before_children`); if `blank_line_before` and the line before the insertion point is non-blank
   and not the heading line, insert one blank line first. Trailing blank lines of the section stay
   after the inserted lines. → `applied`.
6. **`replace_line` / `remove_line`, target found**: among the section's body lines whose `line_hash`
   equals the write's, pick `ordinal` (out of range → the first). Replace with `new_line` or remove the
   line → `applied`. Removing the last own line of a section leaves the section's blank lines as they
   are.
7. **`replace_line`, target missing**: append `new_line + " <!--thock:also-->"` at the end of the body
   → `kept_both`. **`remove_line`, target missing** → `noop`.
8. **`replace_section`, `base_hash` matches** the current `section_hash`: the body is replaced by
   `lines` (trailing blank lines of the section preserved) → `applied`. **Mismatch**: `lines` are
   appended after the body with `blank_line_before: true` and ` <!--thock:also-->` on the first
   appended line → `kept_both`.
9. **Order** is the caller's: `seq` order on the desk, creation order on the phone.

### 8.3 Effect present

| `kind` | Present when |
| --- | --- |
| `create` | the file exists and equals `content` exactly, modulo line endings, or contains `content`'s lines as a contiguous run (the result of rule 3) |
| `append` | the section's body (or the whole file for `null`) contains `lines` as a contiguous run, compared after trimming trailing whitespace of each line |
| `replace_line` | when the target (`line_hash`, `ordinal`) is found: that line **equals** `new_line` (trailing whitespace ignored) or `new_line + " <!--thock:also-->"`; when it is not found: some body line equals either, or has `line_hash(new_line)`. Not a plain hash comparison (a tick keeps the hash), and not "any line equals" either: two identical lines must each be tickable by ordinal |
| `remove_line` | no body line has `line_hash` |
| `replace_section` | `section_hash` equals `section_hash` of `lines`, or the body contains `lines[0] + " <!--thock:also-->"` |

Lines inside fenced code or front matter are never matched and a run never spans them. When a kind
produces more than one structural fact, the outcome reported is the first of `created`,
`section_added`, `kept_both`, `applied`. The stale `replace_section` marker goes on the first
non-blank appended line. `replace_line` and `remove_line` accept `heading: null` for the whole file;
`replace_section` requires a heading.

Known trade-offs, accepted: an `append` whose lines already appear verbatim in the section (the user
typed the same task at the desk) is treated as present and dropped, and one identical line is also
the right outcome; `remove_line` against one of several identical lines removes one per application,
which the effect-present check cannot distinguish, so the desk's re-application after a crash may
remove a second copy.

### 8.4 Rebase and prune on the phone

When a snapshot for `path` arrives at version `v`: `content = snapshot; for each pending write for
path in creation order: content = apply(content, write).text`. Store. Then drop every pending write
with `seq ≤ acked_through_seq` once the phone's cursor is `≥ acked_at_version` (both from `GET /v1/vault`
or the `ack` event). A write that was dropped and whose effect is still visible in a later snapshot
needs nothing; one whose effect is not visible was applied as `kept_both` or `noop` at the desk, which
is the final word.

### 8.5 The conflict marker

` <!--thock:also-->` (one space, then the comment) at the end of a line. Never counted, never nagged
about, never produced by any rule but 7 and 8. The desk conceals it and hints *two versions of this
line* in the gutter; the phone renders the line as any other. `line_hash` ignores it (§7.4 step 5).

## 9. The shared core and its fixtures

### 9.1 The crate

`crates/thock-sync-core/` with `[lib] path = "thock_sync_core.rs"`: no GPUI, no `std::fs`, no async;
builds for `aarch64-apple-ios` and `aarch64-apple-ios-sim`. The desk depends on it directly; the phone
gets it as an XCFramework through UniFFI, generated by `script/build-sync-core-ios`. Public surface:

```rust
pub fn heading_key(text: &str) -> String;
pub fn line_hash(line: &str) -> String;
pub fn section_hash(content: &str, heading: &Heading) -> Option<String>;
pub fn parse_write(json: &str) -> Result<Write, WriteError>;
pub fn effect_present(content: &str, write: &Write) -> bool;
pub fn apply(existing: Option<&str>, write: &Write, seed: Option<&str>) -> Applied; // Applied { text, outcome }
pub fn seal(key: &[u8; 32], context: Context, plaintext: &[u8]) -> Vec<u8>;        // Context::File { path, blob_id } | Context::Write { client_id }
pub fn open(key: &[u8; 32], context: Context, envelope: &[u8]) -> Result<Vec<u8>, SealError>;
pub fn key_check(key: &[u8; 32]) -> String;
pub fn is_syncable_path(path: &str) -> bool;
```

The desk session owns the crate. The phone session consumes it and may, until the XCFramework exists,
port the rules to Swift against the same fixtures; the fixtures are what decide which one is right.

### 9.2 Fixture format

`crates/thock-sync-core/fixtures/v1/<area>/<case>.json`, one case per file:

```json
{
  "name": "tick a line the desk retimed meanwhile",
  "before": "## Day planner\n- [ ] 09:30 - 11:00 Deep work\n",
  "seed": null,
  "write": {"v": 1, "client_id": "…", "kind": "replace_line", "path": "daily/2026-10-02.md", "made_at": "…", "device_id": "…",
            "heading": {"text": "Day planner", "level": 2, "ordinal": 0}, "line_hash": "…", "ordinal": 0, "new_line": "- [x] Deep work"},
  "after": "## Day planner\n- [x] Deep work\n",
  "outcome": "applied",
  "effect_present_before": false,
  "effect_present_after": true
}
```

`before: null` means no file. A runner applies `write` to `before`, asserts `after` and `outcome`, then
applies `write` to `after` and asserts the text is unchanged with outcome `noop`. Areas: `append`,
`create`, `replace_line`, `remove_line`, `replace_section`, `headings`, `line_endings`, `roundtrip`
(`write` is `null`; parse and re-serialise must be byte-identical).

Hash vectors: `fixtures/v1/hashes.json`, a list of `{"line": "…", "line_hash": "…"}` and
`{"text": "…", "heading_key": "…"}`. Envelope vectors: `fixtures/v1/envelope.json`, a list of
`{"key": hex, "nonce": hex, "context": {…}, "plaintext": base64, "envelope": base64, "content_hash": hex}`
plus one `{"key": hex, "key_check": hex}`. Path vectors: `fixtures/v1/paths.json`,
`{"syncable": […], "refused": […]}` for `is_syncable_path`.

### 9.3 Corpus

The fixture corpus required before any side calls itself done: every shipped template under
`crates/thock/assets/`, the V22 example first day, and hand-written notes with frontmatter whose YAML
contains `#` comments, fenced code containing `## not a heading`, tables, HTML comments, nested lists,
CRLF endings, a file without a final newline, duplicate lines in one section, and agent headings at
level 1 after the user's level-2 sections. Each note × each kind × {target present, target changed,
target missing, section missing, file missing}.

## 10. Flows

### 10.1 Pairing

```
Desk                                   Server                                Phone
POST /v1/vault {key_check}  ─────────▶ vault + desk device
POST /v1/vault/pairings    ─────────▶ code, 10 min
show QR thock://pair?code&key&backend
                                                            scan ◀────────────
                                       pair ◀──────────────── POST /v1/vault/pair {code, device_name, apns_token}
                                       tpp_… + vault ───────▶ compare key_check, store key + credential
                                                              GET /v1/vault/files (full pull), download, open, store
                                                              GET /v1/vault/feed
```

### 10.2 Desk upload (foreground edit and catch-up alike)

```
read file → check §4.1 and 2 MB → blob_id = random → envelope = seal(File{path, blob_id}, bytes)
POST /v1/vault/files/{path} {expected_version, blob_id, size, content_hash}
  409 → adopt current.version, retry once
PUT envelope → upload.url
POST /v1/vault/files/{path}/commit {expected_version, blob_id} → version
record (path, version, plaintext hash) locally
```

Coalesce per path with a debounce of two seconds; catch-up on open hashes every allow-listed file
against the local record, uploads differences, tombstones the missing.

### 10.3 Phone write

```
write = document (§7); apply locally (§8) → UI updates
envelope = seal(Write{client_id}, json)
POST /v1/vault/writes {client_id, path, base_version, payload}  → seq   (retry with the same client_id until 2xx)
mark pending write sent(seq)
```

### 10.4 Desk drain

```
on open, and on every `write` event:
  GET /v1/vault/writes?after=<acked_through_seq>  (page until has_more is false)
  checkpoint (V2) once for the batch
  for each write in seq order: open(Write{client_id}) → parse → apply to the file on disk (seed from the template if asked) → write file
  upload every changed file (§10.2) and wait for every commit
  POST /v1/vault/writes/ack {through_seq: last seq}
```

A crash before the ack re-runs the batch next time; rule 1 of §8.2 makes that a no-op.

### 10.5 Phone pull and rebase

```
on feed `file`/`ack`, on silent push, on foreground, on reconnect:
  GET /v1/vault/files?since=<cursor> (page until has_more is false)
  for each row: tombstone → delete local; else if content_hash differs → download, verify hash, open(File{path, blob_id}), rebase (§8.4), store
  cursor = next_since
  GET /v1/vault → prune pending writes per §8.4
```

### 10.6 The three V34 scenarios, as expectations

| Scenario | Expectation that tests pin |
| --- | --- |
| Desk asleep | the phone pulls the last snapshot the desk committed; its writes queue; on desk open the drain applies them in seq order, uploads, acks; the phone's next pull shows them and its queue empties |
| Phone offline | writes stay local, applied to the local copy; on reconnect they are posted in creation order with their original `client_id`s; no duplicates on the server even after retries |
| Same line edited twice | the desk's edit lands in the snapshot; the phone's `replace_line` no longer finds the hash and becomes `kept_both`; both lines are present on both ends after one round |

## 12. Conformance tests

Each codebase pins its side of the contract; a change to this document that breaks one of these is
the signal to talk.

**Backend** (`main_test.go` and friends): every route's success shape and every `code` of §3.3; one
desk and one phone per vault; pairing single use and expiry; `key_check` adoption only on an empty
vault; `409 stale_version` carries `current`; versions strictly increase in commit order under
concurrent commits; `since` paging includes tombstones and the full pull excludes them;
`cursor_expired` after the retention window; write idempotence by `client_id`; ack prunes and records
`acked_at_version`; feed emits for the other device only; quota refusal at quota + 10 %; lapse makes
phone writes `403 plus_lapsed` and phone reads `200`; sweeper deletes after 30 days and not before;
`path_not_allowed` for every §4.1 violation; the local blob mode round-trips bytes exactly.

**Core** (`cargo test -p thock-sync-core`): every fixture passes; applying twice equals applying once;
`roundtrip` cases are byte-identical; envelope vectors open; a blob moved to another path or `blob_id`
fails to open; `key_check` vector matches.

**Desk** (`cargo test -p thock`): catch-up produces the index the disk implies; drain applies in seq
order after one checkpoint and acks only after commits; a `409` retries once with the current version;
files over 2 MB and non-UTF-8 files are listed, not uploaded; the status row strings.

**Phone** (XCTest): the pairing URL parses and a wrong key is refused by `key_check`; full pull then
incremental pull converge with a reference store; rebase keeps pending writes; prune follows §8.4;
retries reuse `client_id`; a lapsed vault goes read-only without losing the local copy.
